# Дизайн: DashScope API Key Checker (веб-версия)

**Дата:** 2026-07-25
**Статус:** одобрен
**Заменяет/улучшает:** `test_api_keys_gui.py` (tkinter) и `test_api_keys.py` (CLI)

## Цель

Сделать чекер API-ключей DashScope более удобным: современный дружелюбный веб-интерфейс, живой прогресс проверки, и возможность скачать готовый файл с проверенными рабочими ключами и моделями, доступными на каждом ключе.

## Решённые вопросы (brainstorming)

- **Платформа:** локальный веб-апп (Python-бэкенд + HTML/CSS/JS фронтенд), открывается в браузере.
- **Архитектура:** одиночный файл `api_checker.py` (встроенная HTML/CSS/JS-строка). Только зависимость `requests` (уже нужна).
- **Формат скачивания:** на выбор JSON / TXT / CSV (кнопки в UI).

## 1. Архитектура

Один файл `api_checker.py`.

### Бэкенд (Python, стандартная библиотека)

Использует `http.server.ThreadingHTTPServer` + кастомный `BaseHTTPRequestHandler`:

- `GET /` — отдаёт встроенную HTML-страницу (CSS и JS встроены в неё как строки внутри Python-модуля).
- `POST /api/check` — **Server-Sent Events (SSE)** поток.
  - Тело запроса (JSON): `{endpoint, keys[], models[], delay, max_tokens, max_concurrency}`.
  - Заголовки ответа: `Content-Type: text/event-stream`, `Cache-Control: no-cache`, `Connection: keep-alive`.
  - События:
    - `start` → `{total, keys:[{index, masked}], models:[...]}` (фронтенд сразу рисует карточки и чипы в состоянии pending)
    - `result` → `{key_index, model, success, message, http_status}` (одно на каждую пару ключ×модель по мере выполнения; фронтенд обновляет соответствующий чип)
    - `done` → `{working_keys, total, elapsed_sec}`
    - `error` → `{message}` (при фатальной ошибке до/во время)
- Запросы к DashScope — через `requests` (как в текущей версии).

### Параллельность

- Несколько ключей проверяются concurrently через `concurrent.futures.ThreadPoolExecutor` с лимитом `max_concurrency` (по умолчанию 5, настраивается в UI).
- Модели в рамках одного ключа — последовательно с задержкой `delay` (бережём per-key rate-limit).
- Готовые результаты пушатся в SSE по мере выполнения (порядок недетерминирован — UI обновляет карточки по событиям).

### Отмена (Стоп)

- Фронтенд закрывает SSE-соединение (`EventSource.close()` / `AbortController`).
- Бэкенд детектит обрыв потока (try/except при записи в `wfile` или проверка флага) и останавливает планирование оставшихся задач через общий `threading.Event` stop-флаг. Уже запущенные HTTP-запросы завершаются, но их результаты отбрасываются.

### Скачивание — на клиенте

Фронтенд сам собрал все результаты из SSE-событий, поэтому файлы формируются в JS (Blob + `<a download>`). Бэкенд-эндпоинт для скачивания **не нужен**.

## 2. Интерфейс (frontend)

Двухпанельный адаптивный лейаут (на узких экранах — стопкой).

### Левая панель — настройки
- Endpoint (префилл `https://dashscope.aliyuncs.com/compatible-mode/v1`).
- Textarea «API-ключи» (по одному в строку).
- Textarea «Модели» (по одной в строке) + кнопка «Загрузить Qwen» (пресет популярных моделей).
- Настройки: Задержка (с), Max tokens, Потоки (max_concurrency) — numeric inputs.
- Кнопки: «▶ Запустить проверку», «⏹ Стоп», «Очистить».

### Правая панель — результаты
- Сводный бар: «X/Y ключей раб.», прогресс-бар, «N/M проверок», время.
- Карточки по ключам (появляются по мере начала проверки):
  - Маскированный ключ + переключатель «👁 показать» (раскрывает полный ключ).
  - Счётчик «✅ X/Y моделей работает».
  - Чипы моделей с цветовым статусом: ✅ OK / ❌ FAIL / ⏳ checking / серый pending.
- После завершения — блок скачивания: кнопки `[JSON] [TXT] [CSV]` + подпись «N рабочих ключей • M моделей».

### UX-детали
- Сохранение настроек и списков ключей/моделей в `localStorage` (восстановление при перезапуске).
- Переключатель светлая/тёмная тема.
- Современный системный шрифт, мягкие тени, скруглённые углы, зелёно-красные акценты.
- Адаптивность под ширину окна.

## 3. Скачиваемый файл

Включаются **только ключи с ≥1 рабочей моделью**. Ключ — **полный (немаскированный)** (для прямого использования). Плюс список рабочих моделей.

- **JSON**
  ```json
  [
    {
      "key": "sk-...",
      "models": ["qwen-max-latest", "qwen-plus-latest"],
      "working_count": 2,
      "total_checked": 3,
      "checked_at": "2026-07-25T14:02:00"
    }
  ]
  ```
- **TXT**
  ```
  # DashScope working keys
  # Checked: 2026-07-25 14:02:00
  # Total working keys: 3
  sk-... | qwen-max-latest, qwen-plus-latest
  sk-... | qwen-turbo-latest
  ```
- **CSV** (стандартный, запятая — разделитель полей; по строке на ключ; модели в колонке `models` объединены через `|`)
  ```csv
  key,models,working_count
  sk-...,qwen-max-latest|qwen-plus-latest,2
  sk-...,qwen-turbo-latest,1
  ```
  > Примечание: `working_count` дублирует число моделей для удобства фильтрации в Excel. Колонка `models` содержит только рабочие модели.

## 4. Обработка ошибок

- Валидация непустых полей (клиент `disable` кнопки + сервер возвращает `error` event).
- Неверный endpoint / невалидный URL — `error` event с понятным текстом.
- Таймаут запроса, сетевые ошибки — `result` со `success:false` и сообщением (как в текущей версии).
- Обрыв SSE при «Стоп» — без ошибок, UI возвращается в состояние «остановлено». В скачивание идут все пары, успевшие получить `result`-событие с `success:true` за этот запуск (включая результаты до нажатия «Стоп»). Блок скачивания доступен, как только собран ≥1 рабочий результат.

## 5. Структура кода (внутри api_checker.py)

Чистое разбиение на хорошо ограниченные секции/функции:

- `HTML_PAGE` — константа с разметкой (включая `<style>` и `<script>`).
- `check_one(key, model, endpoint, max_tokens)` — чистая функция проверки одной пары, возвращает `(success, message, http_status)`. Легко тестировать.
- `run_check_session(payload, send_event, stop_event)` — оркестрация: пул ключей, последовательная проверка моделей, отправка событий. Зависит от `check_one` и колбэка `send_event`.
- `Handler` (http.server) — роутинг `GET /` и `POST /api/check`.
- `build_*` функции форматирования файла живут во frontend JS (чистые, тестируемые).
- `main()` — запуск сервера, выбор свободного порта, автооткрытие браузера (`webbrowser.open`), печать URL.

## 6. Тестирование

- `check_one` — покрыть моком `requests.post` (успех 200, не-200, таймаут, сетевая ошибка).
- Фронтенд-форматтеры `buildJson/buildTxt/buildCsv` — проверить через быстрый прогон в Node/браузере на фиксированном наборе результатов.
- Ручной сценарий: реальный ключ → запуск → проверка живого прогресса → Стоп посередине → повторный запуск до конца → скачивание всех трёх форматов → сверка содержимого.
- Проверить работу при 0 ключей / 0 моделях / нерабочем ключе.

## 7. Запуск

```
python api_checker.py
```
— открывает браузер на `http://127.0.0.1:<порт>/`. Порт выбирается автоматически (например, начиная с 8765, ищется свободный). Ctrl+C в консоли — выход.
